# 대화 원문 보존 및 구축 철학 문서화 운영 규칙

시행일: **2026-10-28 (KST)**  
적용 저장소: **cj01963794-glitch/champions-party-build**

## 목적

사용자와 어시스턴트가 포켓몬 챔피언즈의 파티 구축에 대해 논의한 **원문 맥락**을 잃지 않으면서, 검토를 거친 사고방식을 **docs의 발전 가능한 기준 문서**로 관리한다.

## 1. 두 개의 기록 계층을 분리한다

### conversations/ — 원문 아카이브

- 논의의 실제 발화 순서와 작성자(사용자/어시스턴트)를 기록한다.
- 원칙적으로 발화를 요약하거나 문장을 고쳐 쓰지 않는다. 사용자 동의/반론, 반례, 시행착오를 포함한다.
- 대화에 포함된 이미지·외부 링크·도구 결과 등이 텍스트에 완전히 보존되지 못한 경우 그 한계를 적는다.
- 수집 가능한 범위만 아카이브한다. **접근할 수 없는 과거 대화를 복원한 것처럼 꾸미지 않는다.**
- 날짜·주제별 Markdown을 별도 생성한다. 이미 보존한 기록은 소급 변경하지 않는다.
- 이전 문서에 오기나 누락이 발견되면 정정 기록을 추가하여 변경 사실을 명시한다.

### docs/ — 현재 사용할 구축 사고방식

- 사용자 피드백을 받아 정립한 원칙, 근거, 반례, 판단 기준, 실전 검증 계획을 구조화한다.
- 최초의 **뼈대**는 `TEAM_BUILDING_PHILOSOPHY.md`로 두고, 논의가 축적되면 별도 주제 문서로 세분화한다.
- 단순히 원칙의 개수를 늘리는 대신 기존 원칙의 **조건, 예외, 우선순위, 서로 간의 충돌**을 정리한다.
- 사용자와 합의된 결론, AI의 독립 제안, 검증 전의 가설을 명확히 구분한다.
- 사례 한 개에 맞춘 억지 예외 조항을 무한히 늘리는 방식은 경계한다.

## 2. 대화마다 진행할 기록 절차

1. 논의 중 나온 새로운 주장·반례·피드백을 식별한다.
2. **대화 원문이 접근 가능한 시점에**, 해당 논의의 발화를 `conversations/`에 날짜·주제로 기록한다.
3. 합의된 판단만 `docs/`의 현행 원칙에 반영하고, 미합의 사항은 별도 보류·쟁점으로 남긴다.
4. 변경 이유와 근거, 이전 원칙과의 차이를 `docs/DECISION_LOG.md`에 쓴다.
5. 의미 있는 문서 변경은 `CHANGELOG.md`에 버전과 함께 기재한다.
6. GitHub 쓰기 성공 여부를 확인하고, 실제로 기록된 경로를 사용자에게 알려준다.

## 3. 저장의 범위 및 제약

- GitHub 연동이 가능한 **현재 진행 중인 대화에서 명시적으로 파일 작업을 수행했을 때만** 저장된다.
- 별도의 자동화가 구현되어 있지 않으므로 **모든 메시지의 실시간 자동 백업이나, 채팅 종료 후의 백그라운드 저장은 보장되지 않는다.**
- 다른 채팅방으로 이동하거나 대화가 길어져 일부 내용에 접근할 수 없다면 원문 전체를 확보하지 못할 수도 있다. 그러므로 논의가 길어질 때에는 중간 아카이브를 수행한다.
- `champions-singles-lab` 저장소는 이 프로젝트의 아카이브 작업으로 수정하지 않는다.
- GitHub의 커밋 이력은 문서 개정 기록을 보완하지만, 대화 원문 아카이브를 대체하지 않는다.

## 4. 정리 시 지켜야 할 태도

- *반론이 나왔다*는 사실만으로 기존 원칙이 반증되었다고 취급하지 않는다.
- *합의했다*는 사실만으로 원칙이 보편적 진리라고 취급하지 않는다.
- 일반적인 파티 구축 이론과, 특정 시즌의 환경·기술·도구 등 **검증이 필요한 사실**을 분리한다.
- 파티 실전 구성에서의 선출 가능성, 상대의 합리적 대응, 승리 수순의 견고함을 지속적으로 검토한다.
